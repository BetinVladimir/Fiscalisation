# Fiscal serial ledger and legacy FM lease fence

2026-10-18. New repository API: `ReserveFiscalUNPRange(tenant, serial, fiscalMemoryNumber, count)` reserves under the same tenant+physical serial ledger used by `OpenSaleWithFirstLine`. The fiscal device serial and fiscal memory number are separate, validated identities. Atomic repository locking plus existing persistent generation CAS covers range and immutable identity projection. Disk write failure, including simultaneous failed reload, restores staged memory; online first-line allocation now has the same rollback guarantee.

High-water is the maximum of the serial ledger, every known sale UNP sequence across operators, and all issued serial ranges present in device resources, activation requests and historical issued_binding snapshots. Retired bindings still count: a range is never reused because a route was replaced. New allocation fails before mutation on exhausted/invalid counters or serial/FM identity collisions. Mapping is persisted as immutable `unp_serial_identity`, using tenant+serial digest as resource ID. Cross-tenant historical serial reuse and changing a serial's fiscal-memory identity are deliberately fenced pending explicit transfer/replacement workflow.

Legacy FM-keyed/unscoped counters and previously issued FM-prefix leases return `LEGACY_UNP_LEASE_FENCE_REQUIRED`; merely taking their maximum and renaming the key is unsafe. A device marked REVOKED in backend may still hold a cached offline lease without expiry. Therefore this package does not offer a fake automatic fence-clear flag or treat backend revocation as hardware erasure proof. Activation must surface this explicit migration requirement and use the new API for fresh schema3 authority; it must not call old `ReserveUNPRange` for schema3. After serial identity registration, that old API rejects FM-keyed issuance as well. Central online allocation with a fiscal snapshot carrying FM also performs the same legacy fence checks.

An explicit authorized migration workflow remains required for old estates: enumerate exact affected credential generations and immutable binding/range hashes, prove physical cached authority invalidation or device retirement through a supported vendor/provisioning mechanism, retain independently verifiable evidence, and authorize migration of that exact FM high-water into one unambiguous serial identity. No such proof-producing API currently exists; legacy migration remains blocked instead of being reported complete. FM replacement and cross-tenant transfer require similarly explicit historical identity reconciliation. This is a readiness gate, not a legal assertion.

Executable tests cover shared online/offline counter, restart, all historical range sources, all operators' sale high-water, immutable identity, concurrent disjoint allocation, missing/ambiguous/foreign identities, legacy lease sources (including REVOKED records), old API reenablement rejection, invalid/exhausted inputs and persistence+reload failures for both range and first-line allocation.
