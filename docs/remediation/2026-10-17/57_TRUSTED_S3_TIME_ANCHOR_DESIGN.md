# Trusted S3 time: nonce-bound authority anchor, design for root review

Status: protocol and production integration remain DESIGN, 2026-10-21. Phase1 consumer interval API and Phase2 standalone state core are implemented and host-tested as described below. Production provider, endpoint, cryptographic time verifier and device integration remain unavailable. This closes no runtime/HIL acceptance item. Device private keys remain inside ESP32-S3; ATECC608 is not used.

## Recommendation and decisions

Adopt an internal **time interval authority**, not a scalar clock. Root has approved designing `bounds(lower_unix_seconds, upper_unix_seconds)` (or equivalent explicit window validation). Stage B must require `lower >= issued_at && upper < expires_at` at admission **and publication**. Bounds must be valid, ordered, int64-safe and monotonically published. A single-second-bucket scalar adapter is not the production solution; midpoint, SNTP, mobile time and NVS cached time are not acceptable substitutes.

Recommended implementation sequence after approval: (1) cheap internal interval-interface correction with host fake `[t,t]`; (2) pure nonce/interval state machine and real-crypto Go↔C++ vectors; (3) constrained device request signer + root issuer; (4) opaque relay/bootstrap transport; (5) isolated S3 integration/HIL and only then enable provider. Leave the default unavailable until every dependency and acceptance gate is explicit.

Root decisions still needed: approve protocol V1 fields/domains and proposed limits; choose the server AuthorityClock health source; approve the bootstrap API/device+actor policy; approve initial use of the existing compiled binding-root key via a separate purpose-only signing method, or a separately provisioned time-purpose key. Physical monotonic drift bounds and sleep policy require measurement before production adoption.

## Trust model and bootstrap

Trust a configured root time issuer and its **healthy bounded AuthorityClock**. A signature proves who asserted time, not that their UTC source is correct. A compromised issuer/firmware or unknown oscillator rate is outside what this protocol can repair. Server time must agree with certificate issuance/authorization time through the same AuthorityClock policy; alert and stop issuance when health/error bounds are unknown. Server OS `time.Now()` by itself is not a measured error guarantee. Root may accept a documented authoritative service clock contract; do not relabel it independently verified UTC or НАП certification.

Do not depend on device TLS certificate validity to obtain the first anchor. A phone/backend with its own validated HTTPS session may relay opaque request/response envelopes over a bounded pre-certificate BLE bootstrap control path. Relay time is never trusted. It cannot ask S3 to set time, sign an arbitrary hash, execute a command, install a CA or read keys. WiFi/MQTT/HTTP may carry identical opaque bytes when already usable; protocol safety does not depend on relay TLS to authenticate time. Never disable TLS verification globally to bootstrap a clock. Denial/delay by a relay causes unavailable time.

Proposed API: `POST /devices/{device_id}/trusted-time:anchor` (name provisional; no route exists). Require the same live owner-scoped onboarding authority as certificate activation, plus signed device PoP, active enrolled device key/activation and **current installed signed binding tuple**. A tenant JWT alone does not authorize arbitrary devices. Derive authority from server resources and compare all request fields; root must not sign client-declared tenant/binding facts. Fail closed on repository uncertainty/revocation. Recheck the same authority versions after signing and before publication, following the existing confirmed BLE authority pattern. Rate/size/concurrency limits are mandatory; no financial execution path is reachable.

Initial key option: existing pinned binding issuer key, separate typed method `SignDeviceTimeAnchor` with fixed domain/kind/purpose/schema and source-authority checks. Keep outer and signed inner signer key IDs identical and explicitly allowed for the time purpose. Do not reuse BLE certificate challenge domain. A dedicated time key is stronger key-use isolation but needs an authenticated root-authorized trust catalog and rotation plan; do not accept a PEM/key from the relay or an NVS rollback-able catalog as new authority. Compiled roots define the bootstrap trust floor. Revocation freshness remains an online/backend responsibility, not proof of secure offline anti-rollback.

## Wire V1 contract

Both request and response use an envelope `{canonical_json,algorithm,key_id,signature}` with exact allowed keys, bounded strings and total size ≤4096 bytes. Canonical payload is UTF-8 Go map canonical JSON with sorted keys and exact encoding; decode typed fields, reject unknown/duplicate keys, trailing bytes, NUL/invalid UTF-8, noncanonical escaping/ordering/numbers. Re-encode and byte-compare before verification. Reject `1.0`, `1e0`, negative zero, signed-plus numbers, overflow and noninteger tokens for every integer. Root review correction: wire integers use positive checked int64 with explicit tighter policy limits per field; opaque relays must not parse/re-encode them as JavaScript numbers. The installed legacy binding generation cap remains a separate contract. JSON booleans/strings never coerce to numbers. UUIDs/IDs/hashes use the repository's fixed validation; SHA256 lowercase hex64; nonce canonical unpadded base64url43 chars decoding to32bytes. Reject all-zero, repeated active nonce and boot/request nonce equality. Never use cJSON valuedouble for these fields.

Request canonical fields (no wall-clock timestamp):

- `kind=DEVICE_TIME_ANCHOR_REQUEST`, `version=1`, `purpose=trusted-device-time`, `scope=device.time.anchor`, `policy_version=1`.
- `device_id`, `device_kid`, `device_spki_sha256`, `tenant_id`, `location_id`, `register_id`, `binding_sha256`, `binding_generation`.
- `boot_nonce`, `request_nonce`, `request_sequence` (1..2^31−1), `signer_key_id` (requested pinned root time issuer).

Device signature: P-256 SHA256 over `BEEFISCAL_DEVICE_TIME_ANCHOR_REQUEST_V1\n || canonical_request`; use fixed64-byte P1363 signature in canonical base64url. Add a private purpose-specific request permit/signing method, not a remote generic sign_hash endpoint. Device method constructs nonce/scope internally from the installed authority. Root verifies PoP under enrolled SPKI and exact device_kid; request hash is SHA256 of that **domain-separated canonical transcript**, independent of signature encoding/malleability.

Response canonical fields: `kind=DEVICE_TIME_ANCHOR`, same version/purpose/scope/policy and exact device/scope/key/binding/boot/nonce/sequence fields; `request_sha256`; `server_unix_ms`; `uncertainty_ms`; `max_rtt_ms`; `max_holdover_ms`. Root signature uses P-256 SHA256 with strict DER signature and separate `BEEFISCAL_DEVICE_TIME_ANCHOR_V1\n` domain. Strict DER/base64 bounds and canonical re-encoding apply; response digest/cache identity comes from canonical bytes, not signature representation. Exact policy V1 ceilings proposed: RTT5000ms, holdover30000ms, server uncertainty250ms, resulting max interval width6000ms. Root cannot relax firmware limits via response fields. Server epoch range1700000000000..4102444800000ms. Positive generation ≤2^53−1. These are review values, not existing constants or a device accuracy claim.

Root samples healthy time **after authority/request validation, inside the request's processing interval**, as close to signing as possible. `uncertainty_ms` includes its clock-source error, timestamp quantization and local capture uncertainty. If bounds are unavailable or change during signing, no response. Unknown source precision cannot be replaced with a guessed250ms.

REQUEST_CANONICAL_EXAMPLE.json, RESPONSE_CANONICAL_EXAMPLE.json and EXAMPLES.json are unsigned synthetic layout/hash examples only, not crypto vectors or runtime proof. Go/C++ actual-crypto golden vectors must be created during implementation.

## Device nonce and authority state

States: `UNAVAILABLE → REQUEST_PENDING → ANCHORED`, or `QUARANTINED` on a clock discontinuity/entropy/state fault. Initial boot, deep-sleep wake, reboot, identity reload/change, binding change/generation/hash change, trust-policy change and monotonic reset invalidate both pending request and anchor. Persisted anchor/cert-proof cache does not promote these states. Previously cached certificate proof cannot be returned without a fresh valid authority interval.

Seed dedicated nonce DRBG during safe startup before RF/ADC. Generate boot_nonce32 fresh each boot; request_nonce32 fresh per request from seeded DRBG. Do not persist/restore DRBG state, nonce or authoritative epoch to NVS/SD. Do not reuse provisioning nonce or MAC-derived entropy. Serialize requests: one pending ticket owns boot+binding+identity epoch, nonce, sequence and local monotonic start `m0`. Store m0 before publishing challenge bytes. Entropy/budget exhaustion, all-zero/repeated nonce or sequence exhaustion leaves unavailable; do not wrap counters. Standard bounded request rate protects RNG/crypto budgets.

Request timeout consumes its nonce. Replacement pending request invalidates previous response even if cryptographically valid. Successful install consumes nonce exactly once. Duplicate response is rejected and must not reset the anchor's receive instant, RTT or holdover. An invalid packet cannot consume somebody else's new pending ticket or erase a newer installed anchor; ticket/epoch ownership must be compared before state mutation. For a matching pending response that fails authentication/limits, retire that ticket; retain an existing still-valid anchor only if no authority/clock discontinuity was discovered. Replays across boots fail boot_nonce+pending identity; replaying a stored request to root cannot manufacture a matching fresh device pending challenge.

Verification may run outside locks, but publication must recheck identity, full installed binding and pending ticket under consistent locking. Order: installed-authority guard → provider mutex, including invalidation. Never perform network/signature work holding both; snapshot ticket, verify, then commit with compare. `bounds()` takes only provider state lock and may be called while the existing proof signer holds installed-authority guard. Avoid inverse lock ordering.

## Interval math and monotonic lifetime

Let signed server sample be Tms with certified error Ems. Let `m1` be monotonic instant **after full parsing, signature validation and final installed-authority recheck**, immediately before atomic anchor commit. RTT includes device/relay queue, networking, signing, full body acquisition and verification: `r=m1−m0`, not merely fetch headers. Require r≥0, r≤min(signed limit,firmware cap); all arithmetic checked.

Let device monotonic rate error be bounded by ρ=drift_ppm/10^6 (<1). Firmware/HIL must establish the configured bound; a guessed drift constant is not acceptance. For elapsed monotonic duration d, true elapsed is bounded by `floor(d/(1+ρ)) .. ceil(d/(1−ρ))`. Use integer microseconds/milliseconds, outward rounding and bounded products; do not rely on floating point or target __int128 availability. Bound d before multiplication (30s policy makes checked int64 arithmetic straightforward).

At receipt: `L1=T−E`; `U1=T+E+ceil(r/(1−ρ))`. At local time m≥m1 with d=m−m1: `L=L1+floor(d/(1+ρ))`, `U=U1+ceil(d/(1−ρ))`. This safely treats the server sample as occurring somewhere inside the measured request interval; do not assume symmetric network delay or use midpoint. Max width and holdover remain enforced on **every read**. Compute the worst-case elapsed since sample, `upper_age=ceil((r+d)/(1−ρ))`; require upper_age strictly below max_holdover_ms. Counting only since receipt would permit an extra full RTT of stale authority. Sleep/reset/timer discontinuity or checked overflow means unavailable.

Use integer Unix-second bounds for the current certificate challenge contract: floor(Lms/1000), floor(Ums/1000), with safe nonnegative epochs. Require lower≤upper and lower≥1700000000. Do not round a midpoint into a scalar. Both bounds are inclusive; challenge expiry is exclusive. Exact host fake `[t,t]` remains valid for deterministic tests.

During one authority epoch, published lower and upper must never decrease. Re-anchoring compares new signed interval to the old interval projected to the new receipt instant: disjoint intervals are a clock-discontinuity fault, invalidate authority and fail closed (no silent step, rollback clamp or indefinite reuse of old time). An overlapping interval may be intersected/narrowed, with both output bounds clamped no lower than their last published values, followed by width/age/order checks. If clamping makes policy impossible, return unavailable. New anchors must not revive an expired proof using a lower published upper bound. Widening during holdover is expected only inside configured width/age; widening across a token/challenge boundary rejects that operation even when midpoint remains unchanged.

Initial production policy should invalidate before/after light/deep sleep rather than assuming unmeasured RTC compensation/rate. Espressif documents deep-sleep timer reset; light-sleep compensation exists but does not alone establish this security error bound. CPU frequency changes must be tested with esp_timer; no FreeRTOS tick-derived substitute. SNTP/settimeofday jumps do not affect authority bounds at all; root clock discontinuity does.

## Stage B admission/publication and adjacent authorization

Proposed internal interface: `virtual bool bounds(int64_t& lower, int64_t& upper) const=0;` default unavailable clears/ignores outputs and returnsfalse. `prove()` must independently validate successful output ordering/ranges at **both** reads. At admission and just before output publication: valid current binding/identity + lower≥challenge.issued_at + upper<challenge.expires_at. Only then return cached/new signature. Cache writes or a previously created private permit do not bypass the publication gate. Signature generation crossing expiry, provider loss, widened bounds and binding change must produce empty output.

Do not alter signed Go challenge integer-second fields. Do not add grace/leeway using RTT or uncertainty. A future integration can use the same authority bounds for execution nbf/exp, local tokens and certificate expiry, but requires separate review/tests. Current std::time consumers stay explicit OPEN until migrated. No wholesale settimeofday trust upgrade: UI/log clock can remain conventional while security authority stays separate.

## Root implementation checkpoint

Only Phase1 is accepted and integrated: B now uses inclusive bounds, checks the whole interval at admission/publication and forbids either endpoint moving backwards before publication. Exact host time is [t,t]; production default remains unavailable. Actual Go↔C++/mbedTLS runner PASS40 interval cases plus existing tests. Original scalar-midpoint and removed-monotonic-check counterfactuals are RED. [Evidence](evidence/ble-time-bounds-2026-10-21/root-manifest.json). Inventory above describes the pre-Phase1 snapshot. Remaining wire/bootstrap/clock-health policy is a design proposal requiring implementation review, not an enabled provider. Existing std::time execution/token consumers remain OPEN.

## Phase2: independently verified interval state core

Implemented time_anchor_core.h/.cpp as a standalone core, with no production verifier/provider or runtime wiring. Request ownership binds scope, current boot nonce, request nonce, checked sequence and opaque local ticket. An expired or foreign reply cannot cancel a newer request or refresh an old anchor. Healthy old authority survives refresh only until its original deadline. Boot/binding retirement, monotonic clock loss/backwards and verified disjoint samples fail closed. The bounded recent nonce ring detects repeated output without exhausting the device after128 lifetime requests. Actual fresh boot entropy and server clock-health evidence remain required.

Root GCC15 verification passes5229 independent Python Fraction oracle cases,10050 refreshes, lifecycle/fault tests and three disposable RED mutations. max_rtt_ms limits conservative real elapsed, including drift; the raw-measured-within/adjusted-exceeds boundary is tested. Production compilation excludes the host permit factory and denies raw permit construction. `make time-anchor-test` is now a prerequisite of `make iot-test`. This does not enable trusted UTC, root issuance, certificate installation, actual time-source health or TLS/GATT runtime. Keys remain inside ESP32-S3 NVS; ATECC is unused.
