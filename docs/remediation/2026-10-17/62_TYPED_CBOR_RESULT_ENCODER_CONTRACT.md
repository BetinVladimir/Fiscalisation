Strict mode rejects raw invalid UTF8 and escaped unpaired surrogates, permits valid pairs; no repair. Keep duplicate/trailing rejection. Bound input bytes before parse8192 and strict nesting16; no global JSON canonicalization change. Reject NUL strings/keys for this bridge to preserve existing CBOR profile. New parser entry must have regression proving old Go-compatible repair still works.
3. Add a local `parse_result_value(const char*, size_t, Value&)` helper in ble_result_delivery.cpp (no extra public CBOR API): strict Unicode parse, then recursively normalize lexical Number nodes only when integer() succeeds with canonical signed-int64 decimal token. Reject fractional/exponent forms including1.0/1e0, -0, integer overflow, NaN/Infinity. Do not round Number through double. This is a typed integer CBOR profile, not general float CBOR. Full lexical int64 including above safe53 is accepted because no cJSON conversion occurs.
4. Preserve existing `canonical_json_to_cbor(const cJSON*,...)` as a compatibility wrapper converting to Value under strict recursive checks: finite/integral valuedouble within ±9007199254740991, no valueint read; then exact Integer. Reject duplicate object names, null name/string pointers, invalid UTF8/NUL, unsupported raw cJSON types. No global safe53 relaxation. This wrapper cannot recover already-rounded input and must never become production result bridge again.

Preserve exact aliases COMMITTED→FISCALIZED, RECOVERY_REQUIRED→FISCAL_RESULT_UNKNOWN, COMPENSATED→REJECTED; other string states unchanged as today (client acceptance policy unchanged). Other fields, payment evidence, string references/null/empty collections unchanged. Do not reserialize durable payload, mutate result record or alter ResultSink return handling.

## Wire and resource invariants

Integer major0/1 shortest argument0/1/2/4/8 bytes; signed rangeINT64_MIN..INT64_MAX only, no uint64 extension. Negative argument computed with `-(n+1)` avoiding MIN overflow. Null/bool/string/arrays/maps/struct supported; both map and struct CBOR keys deterministic length-first then UTF8 bytewise, as old encoder. Reject duplicates before encoding (Value permits manually constructed duplicates). Strings remain text; legacy byte-string decode→hex text semantics unchanged (no invented byte node).

Root depth1 matching current typed decoder; max16 inclusive,17 reject. This tightens old encoder's inconsistent root0 rule; production documents are shallow and test proves it. Cap input bytes8192, container cardinality/string byte length8192, output bytes8192 INCLUDING heads. Check remaining capacity BEFORE every push/append/head, subtraction-first checked arithmetic; do not allocate giant intermediate wire vector and reject afterward. Validate full Value tree before allocating output or use bounded writer with transactional temporary output. UTF8 strict validation includes overlong/surrogate/>U10FFFF/truncated/isolated continuation and embeddedNUL policy. No tags/floats/indefinite/record extensions; no signing/hash change implied by CBOR key ordering.

## Accepted implementation refinements

Raw Value::Number is rejected by the typed encoder in every case; only the explicit checked compatibility wrapper/result bridge produces Integer nodes. Existing go_json::parse repair behavior and default limits must remain unchanged; strict bridge input/depth limits apply separately. Actual application waiter/projection tests must consume bigint payment evidence to detect hidden Number/JSON.stringify assumptions beyond a library-only decode test. Production transport remains BFF1. This accepted contract is not implementation or runtime acceptance.
