# Legal and BG-014 activation evidence trust

These gates require independently controlled trust registries and approved candidate requirements outside every respective evidence bundle. Evidence producers must not control those files, their CI environment variables or reviewer keys. Realpath containment and single-link files reject symlink/hardlink aliases into the evidence tree. No actual external key, legal acceptance, hardware evidence or production approval is supplied here.

Runtime: use the same Ed25519-capable Ruby / JSON >=2.18 as [HIL verification](HIL_EVIDENCE_VERIFICATION.md). Full acceptance uses `EVIDENCE_RUBY`, then `HIL_RUBY`, then its own `RbConfig.ruby` for subprocesses. Make verifier tests use `HIL_RUBY`.

```sh
make supto-external-verifier-test HIL_RUBY=/opt/homebrew/opt/ruby/bin/ruby
LEGAL_TRUST_REGISTRY=/controlled/legal/reviewers.json \
LEGAL_REQUIREMENTS=/controlled/legal/candidate.json \
make supto-legal-verify EVIDENCE_DIR=/evidence/legal HIL_RUBY=/opt/homebrew/opt/ruby/bin/ruby
```

The shared `scripts/external_evidence.rb` enforces exact Ed25519 signed bytes, external public SPKI DER SHA256 fingerprint, authorized reviewer role, revocation, expiry, strict UTC calendar timestamps, strict object keys and duplicate JSON-key rejection. No bundled reviewer key grants authority. Legal and activation registry entries extend the HIL registry shape with independently maintained organization, roles and jurisdictions:

```json
{"schema_version":1,"reviewers":[{"reviewer_id":"APPROVED_ID","organization":"APPROVED_EXTERNAL_ORGANIZATION","roles":["LEGAL_REVIEWER"],"jurisdictions":["BG"],"public_key_path":"keys/public.pem","public_key_sha256":"REPLACE_WITH_SPKI_DER_SHA256","revoked":false,"valid_from":"2026-10-01T00:00:00Z","valid_until":"2027-01-01T00:00:00Z"}]}
```

Activation reviewers require role `ACTIVATION_REVIEWER`. Paths resolve relative to registry. Each registry, requirements and public-key realpath must be outside its evidence directory and have exactly one hard link. Protect authority organization identity outside producer-controlled manifests: legal manifest has no reviewer_organization field. A registry organization must match the independently approved requirements and jurisdiction; a legal reviewer organization cannot be Beeloy.

## Candidate subject and legal manifest

External legal requirements and activation requirements have exactly `schema_version:1`, `reviewer_organization` and `subject`. The same candidate subject must be used across legal and activation:

```json
{"jurisdiction":"BG","normative_baseline":"APPROVED_NORMATIVE_BASELINE","product_version":"APPROVED_PRODUCT_VERSION","source_commit":"REPLACE_WITH_40_HEX_COMMIT","build_artifacts":[{"artifact_id":"app","sha256":"REPLACE_WITH_BUILD_SHA256"}],"dossier_artifacts":[{"artifact_id":"dossier","sha256":"REPLACE_WITH_DOSSIER_SHA256"}]}
```

The normative baseline is an independently selected reference/version, not a legal assertion generated by software. Include every approved executable/firmware and dossier artifact. All inventories are nonempty, artifact IDs unique across both groups, hashes 64 lowercase hexadecimal characters, and source commit is full 40-character lowercase Git commit. Fields/IDs/organization are nonempty strings.

Legal bundle contains `legal-acceptance.json`, raw 64-byte Ed25519 `legal-acceptance.sig`, and all subject artifacts. Manifest has exactly:

- `schema_version`: 1; `result`: `ACCEPTED`; `reviewer_id` from external registry.
- `issued_at`, `valid_until`: strict UTC timestamps, covered by reviewer authority, unexpired at verification.
- `subject`: identical approved candidate binding, including jurisdiction, baseline, product, source and all build/dossier hashes.
- `artifacts`: nonempty array of `{artifact_id,path,sha256}`, exactly matching subject inventory.

Artifact paths must be relative without dot/parent/empty components or backslashes. Realpaths must stay within the bundle, including symlinks. Every artifact content hash is checked; duplicate physical paths fail. Unknown fields, duplicate JSON keys, omitted inventory, foreign key, revoked reviewer, expired proof and any changed candidate field fail closed.

## Activation remains production blocked

Activation bundle contains `bg014-activation.json` and raw `bg014-activation.sig`. Its manifest has exactly `schema_version:1`, `profile:"BG_SUPTO_FULL"`, `result:"PASS"`, `reviewer_id`, `issued_at`, `valid_until`, `subject` and `proofs`. Proofs has exactly `hil_manifest_sha256`, `release_manifest_sha256`, `legal_manifest_sha256` matching the actual referenced manifests.

`verify_activation_evidence.rb` additionally requires external `ACTIVATION_TRUST_REGISTRY`, `ACTIVATION_REQUIREMENTS`, and `HIL_EVIDENCE_DIR`, `LEGAL_EVIDENCE_DIR`, `RELEASE_EVIDENCE_DIR` with their own external trust inputs. It runs actual HIL and legal verification, compares their candidate source/build bindings, executes the actual release verifier and compares source. It never substitutes a signed declaration for verified proof consumption.

The current global release contract intentionally accepts only `PROD_NO_GO`. Successful release evidence verification therefore does not authorize activation. Activation unconditionally fails after valid current release proof with `production release contract unavailable (PROD_NO_GO)`; unknown production labels fail the unchanged release verifier. There is no activation PASS route. Before enabling production, implement and review a legitimate production release subject contract that binds approved binaries, product version and normative/dossier subject, plus production security policy and external acceptance. This change does not relax release policy.

Full acceptance delegates activation to this verifier and cannot print a success based on a packaged activation key. Unit fixtures prove legal verification success, proof mismatch rejection, and actual full-gate rejection even when HIL, legal and NO_GO release fixtures all verify. All fixture keys/files are ephemeral test data, never real external acceptance.
