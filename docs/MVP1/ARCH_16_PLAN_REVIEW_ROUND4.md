# ARCH_16 · Ревью MVP1-документации против реальной реализации и ожиданий `docs/` (раунд 4)

Дата: 2026-10-23. Метод: статический. Тесты и сборки **не запускались**; код не менялся. Измерения — скриптами по смонтированному репозиторию (воспроизводимы: см. §6). Оценка токенов приблизительная (≈3.6 симв./токен для кода и латиницы, ≈1.9 для кириллицы; погрешность ±30%).

## 1. Ответы на вопросы

**Q1. Приведёт ли выполнение правок из MVP1 к MVP?**
**Да — к MVP1 в том смысле, как он определён в ARCH_11 (лабораторный HIL: BlueCash-50 + Datecs, наличные/карта/сторно, Beeloy POS → шлюз → Fiscal, E1–E10), при выполнении условий §3. Нет — к тому, что репозиторий сам называет целью**: «MiniPOS/S3/BlueCash» (`docs/system-overview.md`), и тем более к продуктивной эксплуатации: `MVP_GATES.md` держит BlueCash-50 как `EXCLUDED_FROM_PROD`, НАП/юридическая сертификация — отдельный release-blocker «never implied by automated tests».

**Q2. Пригодна ли документация для реализации моделью класса 35B с контекстом 35k?**
**Частично: пригодна для ~⅔ задач после трёх доработок (§4); сейчас — не готова «из коробки».** Сильная сторона: пакет на задачу мал. Слабая: нет инструмента, который отдаёт этот пакет, и ссылки местами неоднозначны.

## 3. Сверка с реализацией и ожиданиями `docs/` (главные находки)

1. **Репозиторий уже содержит свои реестры, а MVP1 опирается на них только транзитивно.** Есть GAP-001…036 (`remediation/2026-10-17/02_GAP_REGISTER.md`), план 70 (карточки P00–P39), срез `fiscal-contour-review-20261021` (FISC-* и 112 критериев unit-тестов), `MVP_BLOCKERS.md`. В MVP1 явно названы 3 GAP; критерии из 112 — 0. Трассировка GAP→Pxx (план 70 §7) → наши ID (ARCH_07 §6) существует, но грубая. Построена автоматическая: `TRACE_EXISTING_REGISTERS.md` (36 GAP: 20 привязаны к карточкам «до HIL», 16 — «после HIL/опционально»; ни один GAP не остался без задачи). Это **транзитивная привязка, не доказательство закрытия**.
2. **Реестры частично устарели относительно кода.** GAP-001 («MQTT namespace не совпадает») помечен OPEN, но `fiscal-backend/internal/mqttclient/client.go:237` уже публикует `tenants/%s/devices/%s/commands`, как подписывается `BlueCashMqtt.kt:46`. Вывод: каждый GAP перед работой **перепроверяется** (DOC-006). Обратное тоже есть: GAP-011 (NAK/SYN/дедлайн) подтверждён кодом как открытый (BUG-029).
3. **Расхождение с `MVP_BLOCKERS.md` (P0-BLUECASH-043).** Блокер: «PM v2.11.4 пишет под cmd 43, что она не используется на BC-50». В тексте PM v2.11.4 (раздел 4.6, cmd 43 «Opening of storno documents») такой пометки **нет**; «не используется на BC-50» — только 33, 35, 47, 61, 63, 80, 106. Но demo-SDK использует собственный `open_StornoReceiptAsync`, и подтверждение Datecs + физический HIL остаются обязательными. Заведена DOC-V7; план сторно (VG-07/08, HIL-BC-06) не меняется.
4. **Контур MVP1 уже, чем «MiniPOS/S3/BlueCash».** S3-прошивка и BLE/provisioning покрыты в MVP1 лишь BUG-040…043 и ссылками на карточки плана 70 (P05–P11, P14, P19, P23–P27). Это допустимо **только** если владелец примет линию отсечения (ARCH_07 R-05: что до HIL, что после) — решение не принято, `execution/mvp-cut.v1.json` не существует (SCR-39).
5. **Известный FAIL вне критериев выхода MVP1.** `sh scripts/verify-contract-lock.sh` падает (FISC-DOC-001; runtime OpenAPI расходится с lock). В ARCH_11 E1–E10 его нет; DOC-003 — P1. Предлагается включить в ворота W1 (иначе «Fiscal API» для POS/MiniPOS не зафиксирован).
6. **Не в MVP1 и не объявлено вне него:** FISC-ACC-001 (сверка с бухгалтерией), MiniPOS-аутентификация P0-AUTH-001 (IdP — внешний). Нужна явная пометка «вне MVP1» в ARCH_11 (сделано как рекомендация R-16.4).

## 4. Что нужно, чтобы слабая модель (35B/35k) работала надёжно

| # | Доработка | Задача |
|---|---|---|
| 1 | Инструмент «пакет задачи»: `scripts/task-pack.py <ID>` собирает карточку + подзадачи + решения + выдержки кода по символам, ≤6000 токенов; режим `--all --check` | **SCR-37** |
| 2 | Нормализация ссылок: полные пути, проверка существования/уникальности и символа в ±30 строках | **DOC-006 / SCR-38** |
| 3 | Запрет `.store-build`, `node_modules`, `dist*`, `build` в поиске: правило в инструкции агента и в `task-pack` | входит в SCR-37 |
| 4 | Закрыть подзадачи без файлов (109) и с общей формулировкой теста (71): при ближайшем касании задачи агент **сначала** дополняет подзадачу по шаблону (файл, функция, вход→ожидание); шаблон — в ARCH_15 §0 | TST-CRIT-01 / DOC-006 |
| 5 | Каждая задача — отдельный чистый контекст: не читать ARCH_01/09/13 целиком; порядок чтения `task-pack` → `DECISIONS.md` (только упомянутые D-n) → файл по диапазону | инструкция агента |
| 6 | Для 16 задач с большими файлами — диапазоны строк в подзадачах (после ARCH-002 `service.go` ≤ 300 строк снимет проблему для backend) | ARCH-002 раньше остальных правок `service.go` |

Что **не** гарантируется даже после этого: корректность тестов-красных, написанных моделью без запуска; поэтому приёмка у каждой подзадачи — команда, а не описание.

## 5. Условия, при которых Q1 = «да»
1. Подтверждены D-1…D-12 владельцем (DECISIONS.md — только рекомендации).
2. Приняты линия отсечения MVP (R-05 / SCR-39) и перечень «вне MVP1» (§3.6).
3. Выполнены зонды PRB-01…05 и вендорный запрос DOC-V7 (PRB-06).
4. Каждый из 36 GAP перепроверен на HEAD (DOC-006) — часть уже исправлена, часть «исправлена» только в отчётах (`REPORTED_PASS`, не `VERIFIED_PASS`).
5. Ответы юриста по NORM-01…16: без них пункты E4/E5/E9 закрываются только консервативными интерим-правилами (DECISIONS §3).
6. Реальные тесты запущены: до этого вся оценка статическая.

## 6. Воспроизведение измерений
Скрипты лежат вне репозитория (`~/w/bundle.py`, `refs.py`, `lines2.py`, `acc.py`, `trace.py` в рабочем каталоге сессии); их перенос в `scripts/` — часть SCR-37/38. Основные команды: подсчёт токенов пакета (`bundle.py`), существование ссылок (`refs.py`), символ в ±30 строках (`lines2.py`), качество подзадач (`acc.py`), транзитивная трассировка (`trace.py`).
