# ARCH_21 · Конвейер поставки: 1 разработчик + qwen3.6-35B (RTX) + codex

Команда: **1 разработчик**, **qwen3.6 35B** на локальной RTX (контекст 35k), **codex** (сильная модель). Конвейер, заданный владельцем: **qwen кодит → сильная модель ревьюит → прогон тестов с багфиксом силами qwen → e2e сильной моделью**. Код продукта этим документом не меняется; здесь регламент, маршрутизация, критерии выхода и оценка срока.

## 1. Конвейер по стадиям

| Стадия | Кто | Вход | Выход | Критерий выхода (автоматический) | Лимит попыток → эскалация |
|---|---|---|---|---|---|

## 2. Что куда помещается (бюджеты контекста)
- **qwen (35k):** системная инструкция ≤ 800 токенов + пакет ≤ 6000 (проверено: максимум 5917 у 300 задач) + файлы ≤ 12 000 + место под ответ ≥ 8 000. Файл > 10k токенов целиком не даётся — только выдержки пакета ±15 строк.
- **codex:** дифф + пакет + чек-лист; крупные файлы разрешены.
- Один запуск qwen = одна подзадача (не вся задача). Диалог не накапливается: каждая итерация начинается с чистого контекста (пакет + свежий дифф + последняя ошибка).

## 3. Маршрутизация (автоматическая)
`python3 docs/MVP1/tools/route-tasks.py --write` строит `execution/routing.json`; `--check` падает, если файл устарел.
Правила: **human** — решения, письма, юристы (DOC/NORM/SCOPE/GATE/PRB/STYLE/W0/MC/CL/SCR, «owner action»); **hil** — физическое устройство; **codex-first** — файл > 10k токенов (сейчас 20 задач с такими файлами: `service.go`, `handler.go`, `repository.go`, `openapi-runtime-v1.yaml`, `App.tsx`, `DatecsPay.cpp`), > 4 файлов кода в подзадачах, либо P0 в критичной области (HMAC, CBOR, ECDSA, NimBLE, mutex, сага, транзакции, питание); остальное — **qwen**. На HEAD: 211 задач qwen, 46 codex-first, 56 human, 1 hil (365 / 170 / 37 / 2 подзадач). Для `codex-first` пишет код codex, поэтому независимое ревью делает разработчик по выборке (каждая 3-я задача) и qwen по чек-листу §4 пунктам 1–8 (дешёвая вторая пара глаз).

## 4. Чек-лист ревью codex (в каждый запрос, 12 пунктов)
1. Деньги только целые центы; нет `parseFloat`/`Number(price)`/`float`/`double` в денежных расчётах; округление half-up `(unit¢×qty_milli+500)/1000`.
2. UNKNOWN ≠ FAILED: после таймаута записи нет повторной записи и возврата карты.
3. Сторно-first (D-12): возврат карты только после подтверждённого фискального сторно.
4. Идемпотентность: повтор с тем же ключом не создаёт второй документ.
5. Любая ошибка хранилища останавливает денежный побочный эффект (GAP-017).
6. Нет «синтетических» номеров документа (GAP-021); номер — из ответа ФУ.
7. Кодировки и кадры: Datecs LEN=data+0x2A, SEQ 0x20…0x7F; Daisy LEN=data+0x24, SEQ 0x20…0xFF; CP1251.
8. Секреты не попадают в логи/коммиты/тесты.
9. Тест из подзадачи действительно падает без правки (проверка на «пустой» тест).
10. Нет изменений вне файлов подзадачи; нет «заодно» рефакторинга.
11. Новые числа в тестах берутся из фикстур или золотого чека (ARCH_22), а не из тестируемого кода.
12. Обработка ошибок типизирована, исключения не выходят наружу из парсеров.

## 5. Шаблоны запросов (коротко)
- **qwen-код:** «Ты исполняешь подзадачу <ID.N>. Правь только файлы из списка. Сначала напиши тест из поля `test`, покажи, что он падает; потом минимальную правку. Верни дифф. Не меняй ничего вне списка. Инварианты: <пункты 1–8 чек-листа>.»
- **codex-ревью:** «Проверь дифф по 12 пунктам. Ответь только JSON `{verdict, findings:[{file,line,sev,fix}]}`. Не переписывай код.»
- **qwen-багфикс:** «Тест падает: <≤150 строк>. Исправь причину в коде, не ослабляй тест. Верни дифф.»
- **codex-e2e:** «Запусти сценарии волны <N> по ARCH_15/ARCH_22 три раза; для красных найди первопричину (продукт / тест / среда) и оформи BUG или правку теста.»

## 7. Сроки (оценка; допущения явно)
Допущения (**ASSUMPTION**, проверяются калибровкой PIPE-03): цикл qwen на подзадачу с ревью и тестами ≈ 25 мин реального времени, из которых разработчик занят ≈ 8 мин; codex-first ≈ 20 мин; доля возвратов по ревью/тестам 30%; HIL-сценарий ≈ 30 мин; разработчик работает 6 продуктивных часов в день, qwen работает параллельно, пока разработчик на HIL/ревью.
- Код: 535 подзадач (365 qwen + 170 codex-first) → ≈ 12 подзадач в день по конвейеру → ≈ 45 рабочих дней; +30% на возвраты = **58 дней**.
- HIL: 48 сценариев ARCH_19 + 40 проверок pos.ble (POS-BLE-01…03) ≈ 88 × 0.5 ч = 44 ч ≈ **7 дней**.
- e2e и исправления (26 сценариев, три прогона, багфиксы): ≈ **8 дней**.
- Итого ≈ **73 рабочих дня ≈ 14,5 недели** при одном разработчике. Нативный BLE в POS (D-13) добавляет к этому POS-BLE-01…03 (около 6 подзадач кода) и 40 HIL-проверок ≈ **+1,5…2 недели**; без D-13 было бы ≈ 12,5 недели.
- **Критический путь не код, а ответы вендоров:** без Q-S2/Q-P4 (Daisy) и Q-B1/Q-B2 (Datecs) пути P-S и P-C остаются в LAB; письма — `docs/vendor/LETTER_DAISY.md`, `LETTER_DATECS.md`.
- Калибровка: после первых 20 подзадач (PIPE-03) пересчитать производительность по `execution/runs/*.json` и поправить цифры выше.
