# ARCH_15 · Спецификации тестов с логикой проверок (E2E и зоны сомнений)

> Назначение: чтобы слабая модель писала тесты **по готовой логике**, а не придумывала ожидания.
> Формат каждого сценария: **Given** (состояние и данные) → **When** (действие) → **Then** (проверяемые утверждения, конкретные числа) → **Oracle** (откуда берётся эталон) → **Автопроверка** (команда).
> Все суммы — EUR, в центах там, где указано `¢`. Фикстуры: `docs/MVP1/fixtures/`.
> Допущения, зависящие от решений владельца, помечены **ASSUMPTION(D-n)** — тест обязан ссылаться на DECISIONS.md.

## 0. Общие правила для всех сценариев

| Правило | Проверка |
|---|---|
| Деньги — только целые центы внутри, строка `^\d+\.\d{2}$` на границах | `rg -n "parseFloat\|Number\(.*price" POS/pos-app/src` не находит денежных расчётов |
| Линия: `line¢ = (unit¢ × qty_milli + 500) ÷ 1000` (целочисленно, half-up), затем `− discount¢` | `fixtures/rounding_golden.json` (34 вектора) |
| НДС из брутто: `net¢ = (gross¢×100 + (100+r)/2) ÷ (100+r)`; `vat¢ = gross¢ − net¢`, считается **по группе**, не по строке | ASSUMPTION(D-4) |
| UNKNOWN ≠ FAILED: после таймаута записи тест проверяет, что НЕ было ни повторной записи с новым ключом, ни возврата карты | счётчики фейков |
| Каждый сценарий печатает в последней строке `E2E <ID> OK` | `grep -q "E2E <ID> OK"` |
| УНП проверяется регэкспом, **уже существующим** в коде (поиск: `rg -n "MustCompile.*[Uu][Nn][Pp]" fiscal-backend/internal/domain`); тест его импортирует и не придумывает формат | регэксп из кода |

Окружение E2E (профиль `e2e-local`): fiscal-backend (Postgres), POS-шлюз (Postgres + RabbitMQ), эмулятор ФУ Datecs (`tools/datecs-sim`, управляемые сбои: `FAIL_AT=<cmd>`, `DROP_AFTER=<cmd>`, `DELAY_MS`), эмулятор карты (APPROVE/DECLINE/TIMEOUT). Запуск: `make e2e-local` (SCR-20).

## 1. Сценарии TST-E2E-01…20

### TST-E2E-01 · Наличная продажа, 1 строка, НДС 20%
- **Given:** смена открыта, часы синхронизированы сегодня; товар «Кафе» 12.00 (1200¢, группа B=20%).
- **When:** POS создаёт продажу qty 1.000, платёж CASH 12.00, финализация с `Idempotency-Key=K1`.
- **Then:** итог 1200¢; `net=1000¢, vat=200¢`; состояние `FISCALIZED`; в ответе непустые `unp`, `fiscalNumber`; чек напечатан и содержит ровно тот же `unp`; в журнале ровно 1 запись фискализации.
- **Oracle:** ручной расчёт выше. **Авто:** `make e2e-local E2E=01`.

### TST-E2E-02 · Карточная продажа
- **Given:** как 01; эмулятор карты APPROVE.
- **When:** платёж CARD 12.00.
- **Then:** команда к ФУ содержит платёж режима из `payment_slots_bc50.json` (CARD→**1**); в шлюзе payment `type=CARD` (не CASH — BUG-055); `card.purchase` вызван 1 раз на 1200¢; `FISCALIZED`.
- **Негатив:** DECLINE → ни одной команды к ФУ (cmd 48 не вызывалась), состояние `PAYMENT_DECLINED`, УНП не израсходован.

### TST-E2E-03 · Смешанная оплата
- **Given:** строки A 7.50 (750¢), B 4.50 (450¢); итог 1200¢.
- **When:** CASH 5.00 + CARD 7.00.
- **Then:** на ФУ два платежа: режим 0 = 500¢, режим 1 = 700¢ (порядок: сначала карта, потом наличные — ASSUMPTION(D-9)); Σплатежей = итогу; в чеке оба платежа. **Негатив:** CASH 5.00 + CARD 6.99 → `PAYMENT_TOTAL_MISMATCH` до любых побочных эффектов (card.purchase=0, cmd48=0).

### TST-E2E-04 · Смешанные ставки НДС
- **Given:** строки: X 10.90 (группа 9%), Y 5.00 (0%), Z 12.00 (20%).
- **Then:** итог 2790¢; разбивка: 9% → net 1000¢/vat 90¢; 0% → net 500¢/vat 0¢; 20% → net 1000¢/vat 200¢; сумма vat = 290¢; ФУ получил налоговые группы по таблице D-11 (A–D); значения в POS-чеке, backend и отчёте совпадают побайтно.

### TST-E2E-05 · Дробное количество
- **Given:** цена 1.99 (199¢), qty 0.333.
- **Then:** линия `(199×333+500)÷1000 = 66¢` в POS, backend, BlueCash и эмуляторе ФУ; платёж 0.66 принимается (`PAYMENT_TOTAL_MISMATCH` НЕ возникает — BUG-023). Все 34 вектора `rounding_golden.json` дают одинаковый результат во всех четырёх реализациях.

### TST-E2E-06 · Скидки
- **Case A (скидка на строку):** 10.00 × 1.000, скидка 1.00 → 900¢.
- **Case B (скидка на чек):** строки 900¢ и 500¢, скидка 140¢ пропорционально → 90¢ и 50¢ (итого 1260¢).
- **Case C (остаток):** строки 333¢ и 667¢, скидка 100¢ → метод наибольших остатков: 33¢ и 67¢ (Σ=100¢ точно).
- **Then:** итоги после скидок: A = 900¢; B = 810¢ + 450¢ = 1260¢; C = 300¢ + 600¢ = 900¢; во всех случаях Σ распределённых скидок равна заданной скидке до цента, команды к ФУ содержат уже распределённые значения, а итог чека равен Σ строк.
- **ASSUMPTION(D-4):** скидка вычитается после округления строки; скидка на чек распределяется пропорционально, остаток — строке с наибольшим дробным остатком. Тест падает, если Σ распределённых ≠ скидке.

### TST-E2E-07 · Offline → синхронизация
- **Given:** шлюз недоступен; POS оформляет 3 продажи (S1,S2,S3) подряд.
- **When:** шлюз поднят.
- **Then:** отправка в порядке S1,S2,S3; у всех разные УНП; повторная отправка S2 (дубликат ключа) не создаёт 4-й документ; общее число документов на ФУ = 3. **Нефискальная печать до синхронизации запрещена** (TST-E2E-19).

### TST-E2E-08 · Таймаут ФУ (UNKNOWN)
- **Given:** эмулятор ФУ `DROP_AFTER=56` (команда закрытия чека получена, ответ потерян); карта APPROVE.
- **When:** финализация.
- **Then:** результат `UNKNOWN`/`RECOVERY_REQUIRED` (НЕ `FAILED`); `card.reverse` = 0 вызовов; cmd cancel (CMD_CANCEL_RECEIPT) = 0 вызовов; затем `reconcile` читает состояние ФУ (cmd 74/76): если документ есть → `FISCALIZED` с реальным номером; если нет → `NOT_FISCALIZED`, и только тогда карта сторнируется (1 вызов). Оба исхода — отдельные подтесты 08a/08b.

### TST-E2E-09 · Полное сторно
- **Then:** сторно ссылается на исходный УНП и дату исходного документа; получает новый УНП ≠ исходного; сумма = сумме исходного; платёж сторно соответствует способу исходного (карта → refund после успешного фискального сторно — BUG-071, наличные → выплата).

### TST-E2E-10 · Частичное и повторное сторно
- **Given:** исходный чек 1200¢.
- **Then:** сторно 500¢ → OK; повторное сторно 800¢ → отказ `REVERSAL_EXCEEDS_REMAINING` (остаток 700¢); сторно 700¢ → OK; ещё любое → `ALREADY_FULLY_REVERSED`. Матрица: `fixtures/storno_matrix.json`.

### TST-E2E-11 · Сторно вне политики
- Исходный чек старше окна политики / другой оператор / другая смена: отказ с кодом `REVERSAL_POLICY_*`.
- **Then:** ответ содержит код `REVERSAL_POLICY_*`; команд сторно к ФУ = 0, возвратов по карте = 0, новый УНП не выдан; в журнале ровно одна запись об отказе с оператором и причиной. **ASSUMPTION(NORM-02/03):** окно и роль берутся из DECISIONS §3 (консервативный интерим: окно из конфигурации `reversal.max_age_days`, по умолчанию 30; роль supervisor).

### TST-E2E-12 · Часы не синхронизированы
- **Given:** `HasDailyClockSync=false` (последняя синхронизация вчера).
- **When:** создание продажи/финализация.
- **Then:** `CLOCK_SYNC_REQUIRED`, ни одной команды к ФУ. После `SyncWorkstationClock` → продажа проходит. Для BC-50 синхронизация = чтение времени cmd 62 + контроль дрейфа (VG-21): дрейф 3 мин → предупреждение (`ClockDriftWarn=5min` не превышен → OK); дрейф 3 ч → блокировка (`ClockDriftMax=2h`). Три подтеста: 0 мин, 6 мин (warn), 3 ч (block).

### TST-E2E-13 · Z-отчёт при незавершённых операциях
- **Given:** одна операция в `RECOVERY_REQUIRED`.
- **Then:** Z-отчёт отклонён `UNRESOLVED_OPERATIONS` (список ID в теле); после reconcile — проходит; счётчики Z = Σ фискализированных чеков смены (сверка с журналом).

### TST-E2E-14 · X-отчёт, внесение/изъятие
- **Given:** открытие кассы 100.00; продажа наличными 12.00; внесение 20.00; изъятие 10.00.
- **Then:** X-отчёт: наличные в кассе = 100.00 + 12.00 + 20.00 − 10.00 = **122.00**; три служебные записи в журнале; изъятие больше остатка (> 122.00) → отказ.

### TST-E2E-15 · Смена даты через полночь Europe/Sofia
- **Given:** тестовые часы: 2026-10-24 23:59:30 Europe/Sofia (UTC+3 — после перехода на зимнее время 25.10 в 04:00 UTC+2; тест фиксирует обе даты).
- **Then:** продажа в 23:59:30 → `business_date=2026-10-24`; в 00:00:30 → `2026-10-25`; в ночь перехода (25.10 03:30 повторяется): `business_date` монотонен, документ не теряется. Все хранится в UTC + явная зона.

### TST-E2E-16 · Электронный чек
- **Then:** до `FISCALIZED` — отправка e-чека запрещена (`EFISCAL_NOT_READY`); после — содержит `unp`, `fiscalNumber`, суммы, дату; хэш содержимого совпадает с журналом. (TG-008, NAP-13: требования уточняются после NORM-12.)

### TST-E2E-17 · Повтор с тем же ключом
- **When:** тот же запрос с `Idempotency-Key=K1` дважды (и ещё раз после рестарта backend).
- **Then:** одинаковое тело ответа, заголовок `Idempotency-Replayed: true`, на ФУ ровно 1 документ, УНП не меняется.

### TST-E2E-18 · Конфликт ключа
- **When:** ключ K1, но другая сумма (1300¢ вместо 1200¢).
- **Then:** `409 IDEMPOTENCY_CONFLICT`, первый документ не изменён.

### TST-E2E-19 · Шлюз недоступен
- **Then:** статус «ожидает фискализации»; печать как фискального документа запрещена; допустима только пометка «НЕФИСКАЛЕН — ожидает» (если политика NORM разрешит; иначе блок продажи). После восстановления — TST-E2E-07.

### TST-E2E-20 · Пустой УНП
- **Given:** мок шлюза отвечает `FISCALIZED` с `unp:""`.
- **Then:** `deliver()` не печатает; статус `NEEDS_ATTENTION`; метрика/лог `FISCAL_UNP_MISSING`; повторный опрос не «лечит» подстановкой `operationId` (BUG-053).

## 3. Как проверить саму спецификацию
`bash scripts/check-test-matrix.sh` (SCR-xx) сверяет: каждый TST-E2E-NN из таблицы ARCH_03 присутствует в этом файле с блоками Then и есть фикстуры; `jq length docs/MVP1/fixtures/rounding_golden.json` ≥ 30.
