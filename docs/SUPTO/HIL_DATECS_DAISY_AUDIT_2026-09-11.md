# HIL-oriented аудит Datecs и Daisy

Дата: 2026-09-11

## Результат программного аудита

| Проверка | Datecs | Daisy | Статус до физического прогона |
|---|---|---|---|
| Группы A/B/C/D | Команда строки передаёт буквенный tax group | Контракт и parser поддерживают восемь slots | Требуется golden receipt для каждой группы |
| CASH/CARD | Реализованы, CARD проходит через terminal authorization | Симулятор различает CARD | Требуется реальный terminal approve/decline/timeout |
| CHEQUE/VOUCHER | Добавлен канонический тип, Datecs использует отдельные payment slots | Требуется подтверждение vendor mapping | BLOCKED |
| NHIF | Канонический тип и reserve slot | Требуется аптечный профиль/программирование названия | BLOCKED |
| DEFERRED | Канонический тип и reserve slot | Требуется подтверждение режима конкретного ФУ/ИАСУТД | BLOCKED |
| INTERNAL_CONSUMPTION | Канонический тип | Применимо только к ЕСФП; текущие Datecs/Daisy retail-модели не доказывают этот сценарий | BLOCKED/OUTSIDE DEVICE PROFILE |
| Z overdue | Backend проверяет readiness | Нужно подтвердить статус ФУ и отказ продажи до auto-Z | BLOCKED |
| Состав чека | API формирует полный receipt summary и QR payload | Физический layout формирует ФУ | Требуется сравнение с чл. 26 и приложениями 1/18/18а |

## Обязательный стендовый сценарий

Для каждой заявленной пары model/firmware необходимо сохранить неизменяемый evidence bundle:

1. Идентичность устройства, FMIN, номер ФП, firmware и свидетельство одобренного типа.
2. Продажа по группам A, B, C и D с raw request/response и фотографией либо сканом бона.
3. Каждый поддерживаемый payment slot после программирования его нормативного наименования.
4. Смешанная оплата и повтор запроса после разрыва связи.
5. Сторно с исходным УНП, номером документа, датой и номером ФП.
6. Состояние в 23:59:59, выключение при наступлении auto-Z и открытый бон через границу дня.
7. Проверка, что до формирования обязательного Z устройство отклоняет новую продажу, а backend не переводит её в успешное состояние.
8. Проверка всех реквизитов чл. 26, QR payload по приложению 18а и фискального логотипа.

## Запрет ложного PASS

Статус `APPROVED_FOR_PROD` для device compliance profile разрешён только при наличии подписанного `HIL` evidence manifest. Отсутствие физического устройства, vendor SDK, merchant/acquirer credentials или свидетельства одобренного типа нельзя заменять simulator-тестом. До загрузки и проверки этих материалов допустим статус `SOFTWARE_VERIFIED`, но не заявление о полном соответствии конкретного аппаратного профиля.
